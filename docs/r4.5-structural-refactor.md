# R4.5 结构重构计划

## 目的与非目标

R4.5 是进入 R5 前的纯结构整理：拆分超大文件、降低模块耦合、收紧领域 API，并让后续生命周期解耦工作建立在可审查的边界上。

R4.5 不引入功能、协议或持久化状态格式变化，不迁移既有状态，不降低 workspace、route、Desktop ownership、反馈 single-flight 或其他安全门禁。R4 的 canonical ExecutionResult、planner-route Result Outbox 和 routed Command canonical-only 回传行为必须保持不变。R4.5 不实现 R5。

## 重构原则

- 先做 behavior-preserving move，再在独立改动中窄化 API；不把搬移和语义重写混在一起。
- 模块按领域事实和状态机职责拆分，导出窄 API；避免为单一实现引入 factory 或空泛 interface。
- composition root 可以向内依赖领域模块；领域模块不得依赖 CLI、Browser 或 UI。
- Routing canonical store、result projector 和 outbox 不依赖 Feedback 或 Browser。
- Browser Companion 保持 return-only，不获得 task-delivery 能力。
- persistent/wire 格式保持不变；确需迁移时必须另立、另审、另授权。
- TypeScript 文件在职责自然时尽量保持约 300-500 行；Python helper 可更大，但不再维持单体文件。
- 每阶段保留现有错误码、命令输出、幂等、锁、原子写与 fail-closed 行为。

## 阶段计划

### R4.5a CLI decomposition

**模块边界**

- 将 `src/cli/index.ts` 收敛为真正的 composition root：创建 program、注册命令组、统一顶层错误出口。
- 按现有命令自然分组提取模块：
  - post-turn-finalizer；
  - desktop-receipt-finalizer；
  - GC / maintenance；
  - runtime lifecycle / status / doctor；
  - setup / tunnel；
  - pairing / logs / workspace / preferences；
  - hidden `record` command。
- 仅 CLI 使用的参数解析、JSON/plain 输出和错误映射可进入一个小型 shared CLI module；领域逻辑继续留在现有领域模块。

**不变量**

- command name、option、default、description、hidden visibility、stdout/stderr JSON 形状和 exit code 完全不变。
- 不改变命令执行顺序、锁、权限、安装、rollout 或 receipt 语义。
- 不将领域实现复制进命令模块。

**测试**

- 现有 CLI contract、record、finalizer、GC、status/doctor、setup/tunnel 与 pairing 测试。
- 工具清单/hidden command 快照或结构断言，确保注册完整且无重复。
- 全量测试、`pnpm typecheck`、`pnpm build`、`git diff --check`。

**退出条件**

- `src/cli/index.ts` 仅承担组装职责；若不引入别扭抽象即可，目标不超过约 500 行。
- 所有命令合同字节级或结构级等价，完整门禁通过并完成独立 review。

### R4.5b TypeScript Desktop IPC decomposition

**模块边界**

- 从 `src/desktop/ipc.ts` 分离 helper process transport/framing、request/response schema、target/identity operations、result ownership/classification operations。
- 对外保留一个稳定 client facade；调用方不直接接触子进程或 wire 细节。

**不变量**

- operation 名称、请求/响应 strict schema、超时、进程身份和错误码不变。
- `chainSignatures`、v2 `deliveryId`、origin alias 与 target-scoped ownership attestation 保持完整。

**测试与退出条件**

- Desktop IPC、result、receipt finalizer、helper protocol/packaging 测试全部通过。
- wire fixture 无变化；各子模块职责单一，facade 不含重复验证逻辑。

### R4.5c Python desktop_ipc helper decomposition

**模块边界**

- 按 transport/framing、Windows process/pipe identity、app-server history normalization、C2C envelope/reconciliation、result ownership/classification、operation dispatch 拆分。
- 保留一个薄的可执行入口和单一 dispatch table；共享 canonical history evaluator，避免 current/target-scoped 两套算法漂移。

**不变量**

- Python 标准库约束、bounded pipe read、单 frame 上限、deadline/overlapped 语义不变。
- history 岛、native continuation、v2 alias、唯一候选、exhausted boundary 与 fail-closed 规则不变。
- 不记录 raw wire、turn text 或凭据。

**测试与退出条件**

- `desktop_ipc_helper_test.py`、`desktop_protocol_test.py`、TypeScript IPC contract 与 packaging tests 全部通过。
- helper 可仍大于 500 行，但 transport、history、ownership 不再位于同一单体模块。

### R4.5d Feedback store/companion domain decomposition

**模块边界**

- Feedback：schema/identity、durable store transaction、receiver binding、projection attachment、reservation/claim/ack lifecycle 分离。
- Companion：pairing intent/credential、route attestation、same-principal rebind、status/bootstrap projection 分离。
- HTTP/MCP handler 仅组装这些领域 API。

**不变量**

- canonical event planner principal 不可变；binding/epoch 仅是匹配 principal 后的 transport coordinates。
- exact-target reserve/claim、single-flight、outcome_unknown、ack 和 takeover fences 不变。
- legacy unpinned 历史兼容保留；Browser Companion 仍为 return-only。

**测试与退出条件**

- production feedback、companion、message、route attestation、Browser architecture separation 全部通过。
- store transaction 只有一个实现，状态机转换由领域模块集中校验。

### R4.5e Desktop result/finalizer/recovery decomposition

**模块边界**

- 分离 current delivery discovery、ownership attestation、trusted receipt/output commit、pending draft staging、detached finalization、unknown/abandon/legacy recovery 共享证明组件。
- receipt writer 与 recovery orchestration 依赖窄的 Desktop evidence API，不直接拼装 helper wire 数据。

**不变量**

- accepted 不等于完成；receipt digest、terminal fence、两次 ownership read、v3 ownership snapshot 与 output atomicity 不变。
- 后续 turn 不得代记，outcome_unknown 只通过严格 reconciliation 恢复。
- R4 canonical projector 继续只消费 trusted receipt，不读取 Browser 状态。

**测试与退出条件**

- Desktop result/CLI/finalizer、unknown reconciliation、abandonment、legacy reconciliation/retirement、R4 result reconciliation 全部通过。
- immediate 与 detached finalization 复用相同的证明/commit primitives，无交叉依赖 Feedback。

### R4.5f Secondary cleanup and boundary enforcement

**模块边界**

- `src/session/state.ts`：schema/compat read、transaction、checkpoint/session operations 分离。
- `src/workflow/readiness.ts`：事实模型、纯策略决策、projection 分离。
- `src/mcp/server.ts`：server composition 与各 tool group registration 分离。
- 拆分超大测试文件，优先按领域状态机和公开合同组织，不复制 fixture 逻辑。

**不变量**

- request-scoped principal、Desktop/Remote capability scope、saved/current binding 策略不变。
- MCP 工具名、schema、visibility、OAuth scope 与错误映射不变。
- 新增 architecture tests：domain 不依赖 CLI/Browser/UI，Routing 不依赖 Feedback/Browser，Companion 不获得 task delivery。

**测试与退出条件**

- readiness、workflow request/MCP projection、session、MCP integration 与 architecture separation 全部通过。
- composition root 只注册工具；纯决策函数可独立测试；超大测试拆分后覆盖数量和关键负例不减少。

## Review 与回滚策略

- 严格按 R4.5a-f 分阶段实施；每阶段只包含一个可说明的结构边界，不做 mega-diff。
- 每阶段先机械移动并证明行为等价，再决定是否需要后续 API 收紧；不预建未使用抽象。
- 每阶段独立运行定向与完整门禁，提交前接受独立 review，部署也需单独授权。
- 每个阶段形成独立 commit；发现回归时可整阶段 revert，不依赖状态迁移或跨阶段半成品。
- 任一阶段若需要 wire/state schema、协议或行为变化，停止并拆成新的授权任务，不以“结构重构”名义夹带。
